The engines

Independent engines.
One workshop.

Independent engines, each with a job.

Each engine has its own scope, documentation and repository. Start with the task in front of you.

Ferroni

A regex engine

Runs Oniguruma's regular expressions in Rust, lookbehind, backreferences, named groups and Unicode classes included, with the multi-pattern scanner that editors and highlighters drive built in.

Explore FerroniProject site

Ferriki

A syntax highlighter

Highlights code with the grammars and themes your editor uses, from Node.js, from Rust, or at build time in Vite.

Explore FerrikiProject site

Ferromark

A Markdown renderer

Turns Markdown into HTML, sanitized by default, and is among the fastest engines for the job.

Explore FerromarkProject site

Ferrolex

A spell checker

Checks spelling in prose and in code, and gives the same suggestions every time.

Explore FerrolexRepository

Ferrocat

A translation catalog engine

Reads, merges, and compiles translation catalogs.

Explore FerrocatProject site

Ferralk

A glob matcher and file walker

Matches glob patterns and walks file trees in parallel, ahead of globset and fast-glob.

Explore FerralkRepository

Ferrugo

A PDF preview renderer

Renders previews of PDF files you have no reason to trust.

Explore FerrugoRepository

Ferrolink

A link checker for static sites

Checks page links, asset references and anchors in static HTML builds, without a server or network requests.

Explore FerrolinkRepository

Ferrigura

A diagram renderer

Renders Mermaid diagram text as SVG in Rust, with embedded fonts and no browser.

Explore FerriguraRepository

The workshop

Built with care.
Adopted independently.

Shared workmanship.
Independent tools.

Take the tool you need.

The family is a way to find related work, not a required stack. Each engine keeps a focused purpose. Where two fit together, their documentation explains the relationship.

Ferriki uses Ferroni for pattern matching and pairs with Ferromark for highlighted documents. Ferromark does not require Ferriki.

Keep the evidence close.

Read the reference tests, compatibility notes and measurements in each repository. That is where the conditions stay attached to the claim and where limitations can be checked against your workload.

Use the engine's own documentation to understand the interfaces and boundaries that matter to your application.
